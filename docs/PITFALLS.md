# 踩过的坑（quick-login）

> **为什么要有这个文件**：这里每一条都是**"看起来正常但其实是坏的"**那一类 ——
> 它们不抛异常、测试也未必覆盖，只是静默地变差。类型系统和构建都不拦这些。
>
> **格式（与 `akso-vault/docs/PITFALLS.md` 一致，五段）**：
> 症状 / 根因 / 判据 / 处置 / 推广。**编号是稳定 ID，永不重编**；已修的不要删，
> 改状态标注即可 —— 它的价值在于让下一个人知道**这里曾经坏过、以及坏成什么样**。
>
> **每条必须有可执行判据**。写不出判据，说明还没定位到根因。
>
> 本仓此前**没有**这个文件，这类教训散在 `CHANGELOG.md` 里。`CHANGELOG.md` 记的是
> "每次发布改了什么"，本文件记的是"**哪些错会静默发生、怎么一眼认出来**"——
> 前者是历史，后者是可复用的判据。

## #1 【已修】`urlTransform` 是 Firefox 专属 ⇒ 整个网络平面曾一起死掉

**症状**：多开时 HTTP 缓存平面失效，四个账号互相串缓存；而**更糟的是**——
COOKIE 与 AUTH 平面的规则也一起没生效。

**根因**：平面 4（HTTP 缓存）用 DNR 的 `redirect.urlTransform` 实现，
而**该字段是 Firefox 专属、Chrome 从未支持**（Chromium 以
`Unexpected property: 'urlTransform'` 拒绝）。关键在于
**`updateSessionRules` 是原子批量操作** ⇒ 同一批里的 COOKIE / AUTH 规则被连坐拒绝，
**网络平面全死**。而失败信息只说"属性不认识"，不指向"另外两个平面也废了"。

**判据**：`Get-ChildItem packages/extension/src -Recurse -Filter *.ts | Select-String -Pattern 'urlTransform\s*:'`
⇒ **零命中**。★ 必须匹配**作为键**的 `urlTransform:`，**不要**只搜这个词 ——
它在解释"为什么不用它"的注释里有 4 处，只搜词会**永远为红**。
已实测：精确判据零命中，且构造一个真实使用后**能红**。

**处置**：**已修**。改为页面层实现 + **逐条安装降级**
（一条规则被拒不再连坐其余）。

**推广**：★ **批量原子 API 的失败面是"整批"，不是"那一条"。**
用这类 API 时，问的第一个问题不是"这条对不对"，而是
**"这条错了会带走谁"**。同理适用于 `chrome.declarativeNetRequest.updateSessionRules`、
`runtime.sendMessage` 的批量场景、以及任何事务型批量写。

## #2 【已修】`shield-main.ts` 的四个平面**漏了 `?` 号** ⇒ 内网 http 站点全不生效

**症状**：内网形态是**纯 http**（`10.100.0.105`），而那四个平面的补丁**只对 https 生效**，
于是内网站点串号；而公网站点一切正常 ⇒ 报障时容易判成"内网平台的问题"。

**根因**：补丁里手写 origin 匹配时漏了 `?`（`https?` 写成了 `https`），
而**漏一个字符不报错**——它只是"这条分支永远不进"。

**判据**：`Select-String -Path packages/extension/src/content/shield-main.ts -Pattern 'https\?:'`
⇒ 命中数 == 需要 scheme 无关的平面数。

**处置**：**已修**（v3.10.9）。并由此引入"**scheme 必须数据化**"这条约定：
站点协议 hint 存在 `LOCAL_KEYS.siteSchemes`，不在代码里写死。

**推广**：**目标环境有两种形态时，第二种形态是最容易漏的。**
本仓的目标平台同时有公网 https 与内网 http ⇒ 任何"只在 https 下测过"的改动
都只覆盖了一半用户。

## #3 【已修】日志面曾**没有脱敏通道**，且 logger 命名空间分叉

**症状**：无 —— **改造前只有 3 处裸 `console.*`，都"看起来没用凭据"**。
所以"还没有凭据泄露"这件事**只是碰巧**。

**根因**：两个独立的问题叠在一起：

1. `console.debug('[ql-auto] submit rejected by server', { errorSeen })` 这种
   **对象直传**是典型形态 —— 今天 `errorSeen` 里只有计数，明天有人往里塞
   `{ username, password }` 做"排障方便"，凭据就出去了，**而没有任何东西会拦住**。
   本扩展**持有用户在各平台的真实口令**（填表要用），所以这条代价极高。
2. 服务端（`akso-vault`）同期还有第二套 logger 名的问题（那边已记为它的 #7）——
   这里写下来是为了记住**两端的日志形状应当一致**，否则读日志的人要多一次上下文切换。

**判据**：`node tools/verify/log-redaction.mjs` —— 37 条断言，两侧都测：

- **该打掉的**（漏了就是外泄）：`password=` / `"secret":` / `token:` / `Bearer` /
  `Basic` / URL 查询串里的 `device_code` 与 `user_code` / `fermeyKey` / 裸长十六进制；
- **不该打掉的**（过度匹配会让日志失去价值，于是有人去关掉打码 —— 那是下一条泄露路径）；
- **端到端**：`log()` 出来的东西（含**对象直传**与**分隔参数**两种形态）都不含凭据原文；
- **结构性**：`src/` 下除 `shared/log.ts` 外**零裸 `console.*`**。

★ 并做了**反证**（`tools/verify/falsify-log-redaction.mjs`，3/3）：
把 `formatArgs` 改成直接返回原文 ⇒ 验收如期变红；还原后逐字节一致。

**处置**：**已修**（2026-10-09）。新增两个共享模块：

```
shared/redact.ts   纯函数的打码规则（可单独测试）
shared/log.ts      getLogger(ns) —— 所有出口都只经由 log()，而 log() 无条件先打码
```

三条设计决定，理由都是"绕不过去"：

1. **打码在 `log()` 里，不在调用点。** 调用点靠自觉，而自觉会失效。
2. **先做 `%s` 替换、再打码。** 理由见 #4（这是实测踩出来的）。
3. **对象必须先序列化再打码**，且序列化**绝不能抛**（循环引用 / BigInt /
   `undefined`）。★ MV3 的 SW 里一个未捕获异常会**终止整个 worker** ——
   日志代码把业务带崩，比丢一条日志坏得多。

**推广**：**"凭据不入日志"必须是结构，不是纪律。**
与 `akso-vault` PITFALLS #1 是同一条推理的两个应用面。

## #4 【已修·判据教训】`%s` 会把"键"和"值"分开，于是打码**完全失效**

**症状**：`logger.info('password=%s', secret)` 打出来的日志里，
**口令是明文**，而单测 `redact('password=xxx')` 却通过。

**根因**：格式器如果只是把参数用空格拼起来，上面那句会变成
`password=%s secret` —— **`%s` 夹在键和值中间**，
打码规则看到的是"一个孤立的词"，于是**没有任何规则命中**。

★ 这是本轮最值得记的一条，因为**它的两层测试会给出相反的结论**：
纯函数层全绿（`redact` 本身没问题），只有端到端层会红。

**判据**：`node tools/verify/log-redaction.mjs` 第 4 节那条
「log() 里的分隔参数口令被打掉」。反证：把 `interpolate` 换回纯 `join(' ')`
⇒ 该条如期变红。

**处置**：**已修**。`formatArgs` 的顺序固定为
**先 `%s/%d/...` 替换 → 再拼多余参数 → 最后整体打码**。
顺序不能反：替换让"键 = 值"重新贴在一起，打码才有东西可认。

**推广**：★ **"打码函数是对的"与"打码在实际路径上生效"是两件事。**
凡是"先格式化再脱敏"的通道，都必须有一条**走真实出口**的用例 ——
只测纯函数会给出虚假的安全感。

## #5 【已修·判据教训】esbuild 摇树把没被 `import` 的导出删掉 ⇒ 验证脚本"找不到函数"

**症状**：验证脚本从 `shared/log.ts` 解构 `redact` / `REDACTED` 时报
`TypeError: redact is not a function`，而源码里明明写着 `export function redact`。

**根因**：`log.ts` 只 `import { redact } from './redact'` ⇒ 打包时
**esbuild 把 `redact.ts` 里没被用到的导出整段摇掉**（包括 `REDACTED`）。
导出在**源码**里存在、在**产物**里不存在 —— 而报错只指向"不是函数"。

**判据**：验证脚本能取到它需要的每个导出（现由 `log-redaction.mjs` 隐式覆盖：
它解构了 `redact` / `REDACTED` / `formatArgs` / `getLogger` / `setLogLevel` / `drain`）。

**处置**：**已修**。`log.ts` **显式转发**打码 API：

```ts
export { redact, REDACTED, REDACTION_RULES } from './redact';
```

这不只是整洁 —— 它让 `log.ts` 成为日志相关的**唯一公开面**，
调用方不会去 import 一个"其实不会被打进产物"的内部模块。

**推广**：**`export` 是源码层的概念，产物里有什么由打包器的摇树决定。**
凡是用"现场转译源码"的方式做验收（本仓 `tools/verify/log-redaction.mjs` 就这么做），
入口的导出面必须与验收脚本的需要一致。

## #6 【已修·判据教训】仓库根算错一层，**不报错、只指向错目录**

**症状**：脚本报 `Could not resolve ".../tools/packages/extension/src/shared/log.ts"`
—— 路径里多了一层 `tools/`，而**脚本本身没有任何语法或运行时错误**。

**根因**：惯用法 `path.resolve(path.dirname(fileURLToPath(import.meta.url)), '..')`
在**一层深**的目录里（`tmp/x.mjs`）正好是仓库根；搬到 `tools/verify/`（**两层深**）后
必须写成 `'..', '..'`。**少一层不报错，只会指向错目录。**

**判据**：把表达式**真的求值**并断言等于仓库根。本仓的做法是脚本开头打印
`ROOT = ...` 并在启动时对关键路径做 `existsSync` —— 让"指错目录"立刻可见。

**处置**：**已修**。`tools/verify/log-redaction.mjs` 用 `resolve(HERE, '..', '..')`，
并在注释里写明"少一层会静默指向 `tools/`"。
★ 本轮**又踩了一次**：临时调试脚本 `debug-bundle.mjs` 第一次写的就是一层，
报错信息看起来像"esbuild 配置有问题"。

**推广**：★ **这类错误的特征是"报错指向别处"。**
凡是脚本依赖"我在目录树的第几层"，就把它**打印出来**或**断言**一次 ——
靠肉眼数 `..` 的个数，迟早数错。

> **同一根因的相反表现（本仓无 `.gitattributes`，`akso-vault` 有）**：
> 两个仓库对行尾的处理**方向相反**，所以同一个"行尾不对"的毛病在两边长得完全不一样：
>
> | 仓库 | `.gitattributes` | 索引里存的 | 磁盘上检出的 | 症状 |
> |---|---|---|---|---|
> | `akso-vault` | 有（`*.py text eol=lf`） | LF | **LF** | 脚本把文件写成 CRLF ⇒ `git status` 长期一堆**假 `M`**，真的改动看不见 |
> | `quick-login` | **无** | LF | **CRLF** | 每次提交打印一堆 `LF will be replaced by CRLF` 警告（**装饰性**，内容无差异） |
>
> ★ 本仓实测**没有**假 `M`（提交后 `git status` 干净），所以**刻意不加** `.gitattributes`：
> 加它会对上百个已跟踪文件做一次重规范化，产生一个巨大且无实际收益的 diff。
> ⇒ **"看到警告就改配置"不是判据；先确认它有没有造成实际损害**（这里是"有没有假 M"）。
> 本仓的脚本都在 Windows 上跑、或由 `npm` 调起，shebang 的行尾不会成为问题。

## #7 【已修·判据教训】`window===window.top` 判顶层，在 `srcdoc` iframe 里会给出反直觉结果

**症状**：自动填表在密码框位于同源 `srcdoc` iframe 时，**顶层 frame 也要去填**，
但脚本按"只有子 frame 才填"的分支走 ⇒ 填不上，而日志里"看起来走对了分支"。

**根因**：`about:srcdoc` frame **不会被 `<all_urls>` 的 content script 注入**
⇒ "谁负责填密码"不能按"我是不是顶层"来决定，必须按
**"我能不能拿到那个 `iframe.contentDocument`"** 来决定。

**判据**：`docs/CODEBASE_OVERVIEW.md` 里记录的填充分工
（顶层 frame：用户名 + 访问 srcdoc iframe 填口令 + 勾协议 + 提交；
子 frame：仅兜底填自身 frame 内的口令）必须与实际分支一致。

**处置**：**已修**。填充逻辑按"能否访问 `contentDocument`"分支，
而不是按 `window === window.top`。

**推广**：**"我在哪"和"我能碰到什么"是两件事。**
按位置分支容易写对、也容易漏；按能力分支更贴近真实约束。

## #8 【已修·设计确认】`updateSessionRules` 是**原子批量**，必须逐条降级

**症状**：新增一条 DNR 规则后，**别的平面的规则也一起失效**，
而报错只说"新加的那条不认识"（见 #1 的实测）。

**根因**：Chrome 的 `updateSessionRules` 对整批做原子校验 ——
一条不合法，整批不生效。⇒ "新加一条规则"这个动作的**失败面是整个网络平面**。

**判据**：`tab-rules.ts` 必须是**逐条安装**（每条单独调一次），
并记录每条的结果；而不是把 N 条拼成一个数组一次提交。

**处置**：**已修**。逐条安装 + 每条单独捕获。

**推广**：**"加一条"的风险不等于"那一条"的风险。**
用批量原子 API 时，新条目的爆炸半径是**整批**。

## #9 【已修·设计确认】身份类 cookie 黑名单必须**集中声明**

**症状**：`mergeCookieSnapshot` 的 token 门禁与 `IDENTITY_COOKIE_BLACKLIST`

**根因**：黑名单是"同一件事的两个声明点"。

**同一事实不要有两处声明**。两处各写一遍，迟早出现"改了一处、另一处没改"。

## #10 【已修·设计确认】验证脚本必须入库，**`tmp/` 是 gitignored**

**症状**：20 个验证脚本曾在 `tmp/` 下，`git ls-files tmp/` = **0** ⇒
换机器 / 新 clone / CI **一个都拿不到**。同类损失此前已发生过一次
（`tools/e2e/` 整套在收束清理中被删）。

**根因**：`tmp/` 是运行产物的目录（Chrome 档案几百 MB，不该入库），
但"脚本"与"脚本的产物"被混在了同一个目录里。

**判据**：`git ls-files tools/verify/` 的条数 == 该目录下的脚本数；
且 `git ls-files tmp/` 中的 `.mjs`/`.ts` 数 == 0。

**处置**：**已修**。脚本迁到 `tools/verify/`（入库），运行产物留在 `tmp/`（不入库）。

**推广**：★ **"临时"这个属性会传染。**
把脚本放进 `tmp/` 的那一刻它就被判了死刑，而**没人会注意到**，
因为文件在本地一直在、跑起来也一直正常。

## #11 【已修·判据教训】幽灵依赖：`node_modules` 里有 ≠ 能复现

**症状**：换机器 `npm ci` 后所有验证脚本报"找不到模块"，
而开发机上**一直跑得好好的**。

**根因**：**3 个幽灵依赖**（`playwright-core` 全部脚本用、`@peculiar/x509` 与
`reflect-metadata` 3 个自签 https 脚本用）只存在于 `node_modules/`，
`package.json` 与 `package-lock.json` 里都没有。
它们来自历史上某次 `npm install --no-save`。

**判据**：`npm run check-deps` ⇒ `DEP_OK`。
★ 该门禁自身也踩过坑（详见 `tools/check_deps.mjs` 的注释）：
第一版在源码上跑正则 ⇒ 假阳性（把注释里的 `import` 当依赖）；
改成"先剥字符串"后 ⇒ 说明符被清空、**检查数从 27 掉到 0，门禁退化成"永远绿"**，
而它打印的「检查 0 处」看起来完全正常。现在它带自检：
一处三方模块都没扫到就报 `DEP_SUSPECT`。

**处置**：**已修**。三个依赖写进 `devDependencies`；加 `npm run check-deps` 门禁。

**推广**：★★ **"能跑 ≠ 可复现"。**
加依赖一律 `npm install --save-dev`；`--no-save` 装上的东西会在
换机器时**同时消失、且只在别人的机器上暴露**。

> 这条与 #10、以及 `akso-vault` PITFALLS #11 是同一条主线的三个面：
> **"在我机器上是对的"这件事，不能作为判据。**

## #12 【已修】有三个写日志的出口，只有一个是受控的 —— `forensics` / `diag` **绕过打码**

**症状**：源码里"零裸 `console.*`"（判据绿）、`shared/log.ts` 的打码 37/37 通过、
诊断包能正常导出。一切看起来都对。

而实际上扩展端有**三个**把信息写出进程的出口：

| 出口 | 落点 | 当时是否打码 |
|---|---|---|
| `shared/log.ts` 的 `log()` | DevTools + 环形缓冲 | ✅ 强制打码 |
| `forensics()` | `storage.local['ql:forensics']`（**环形 120 条**） | ❌ **无** |
| `diag()` | `storage.local['ql:diag']`（**环形 60 条**） | ❌ **无** |

后两个的产物会**进诊断包被一键导出** —— 一条凭据进 `forensics`，
就等于**永久落在磁盘上、并且被导出去**。

**根因**：安全保证建在**约定**上，而不是**机制**上。
`content/auto-login.ts` 的注释写着"密码/用户名绝不入日志"，7 个 `report()` 调用点
**当时确实遵守了**（只传 `attempts` / `reason` / `errorSeen` / `btnText`）。
但：

- 载荷是 `{ tabId: sender.tab?.id, ...p }`，而 **`p` 完全由内容脚本决定**；
- 没有任何东西阻止下一个人写 `report('x', { password })`；
- `forensics` 是 `export` 的 —— **任何模块都能直接调**。

⇒ "我当时检查过所有调用点"不是一种可持续的保证。

**判据**：

- `node tools/verify/verify-forensics-redaction.mjs`（**25 条**）。
  它不是读代码猜，而是**真的把 `parallel-session.ts` 求值、真的调 `forensics()`**，

## #13 【已修·判据教训】花括号配平从**签名开头**数，会被参数表里的 `{}` 骗到

**症状**：一条"断言某函数体里调了 `redact()`"的结构判据**恒假**（假红），
而且它两次假红的原因是**两个不同的**坑。

**根因**（两次都值得记）：

1. **第一版**用 `ps.indexOf('function ' + name + '(')` 定位 —— 而实际声明是
   `export async function forensics(`，前面有 `export async` ⇒ **找不到**，
   函数体返回空串，`''.includes('redact(')` 恒 `false`。
2. **第二版**改成正则后**仍然假红**：花括号配平**从签名开头**开始数，
   而参数表里就有 `detail: Record<string, unknown> = {}` ——
   那个 `{}` 让 depth 先 `+1` 再 `-1`，于是**数到参数表末尾就归零了**，
   只截到 81 个字符（正好是签名那一行）。

**判据**：

- 定位函数体必须先用 `)\s*{` **跳过参数表**，从函数体的 `{` 起配平。
- ★ 并且**"找不到函数体"必须判失败**，不能静默返回空串、再靠后续断言碰运气 ——
  那样失败信息会指向"没调 `redact`"，而真因是"判据没找到函数"。
- 本轮的做法：先加两条 `check('能定位到 X 的函数体（判据自身的前提）')`，
  让"前提不成立"与"断言不成立"在输出里**分得开**。

**处置**：`tools/verify/verify-forensics-redaction.mjs` 的 `bodyOf()` 按上述写法。

**推广**：★ **写"代码结构"类判据时，先验证"我能拿到那段代码"。**
  拿不到时的表现是"断言为假"，而它读起来像"代码有问题" ——
  于是你会去查**被测代码**，而问题在**判据**。
  ⇒ 结构判据要有一条**自证前提**的断言（"我确实取到了这段代码"）。

   ⇒ 判据必须落在**那个具体分支**上。

**推广**：★ **"加日志"包含三件事，缺一件就等于没加**：
① 有出口、② **有人读**、③ **有用的那条活得到被读的时候**。

## #15 【已修】同一个类型被声明了两次 —— 而现在"不出问题"靠的是一个**实现细节**

**症状**：一切正常。离线回落工作、列表能看、写路径如实报错、`tsc` 零错误、
打码 54/54 通过。**没有任何症状。**

**根因**：`OfflineError` 与 `isOfflineError` 被声明了**两份**，
而且**逐字相同**：

| 文件 | 角色 |
|---|---|
| `background/core/offline.ts` | 文件头明确写着"**单独一个模块，为了让 `cloud-store` 与 `parallel-store` 都能用**" |
| `background/core/parallel-store.ts` | **又写了一遍**同名类 + 同名函数 |

它当时**确实不会出错**，原因是一个**实现细节**：判定用的是**标记字段**

```ts
e.isOfflineError === true        // ← 靠它，两份类定义产生的实例互相认得
```

而不是 `instanceof`。而 `offline.ts` 的文件头**恰好警告过这件事**：

> 循环依赖在 `iife` 打包下不报错，只会在运行时给出 `undefined` ——
> 那时 `instanceof` 永远为 false，**回落静默失效**（表现是"离线时列表空了"）。

⇒ 于是形成一个很难察觉的处境：**"现在是对的"依赖"没人把判定改成 `instanceof`"**，
而 `instanceof` 看起来是**更正规**的写法 —— 下一个人"顺手规范化"它，
离线回落就**静默失效**，症状是"离线时列表空了"，没有任何报错指向这里。

★ 这条与本仓 #9（身份类 cookie 黑名单必须集中声明）、
akso-vault #14（同一事实不要有两处声明）是**同一条主线**：
**两处声明同一事实，一致时无收益，不一致时的失败是静默的。**

**判据**（`tools/verify/verify-log-redaction.mjs` 第 8 节，**54 条**）：

- `export class OfflineError` 全仓**恰好 1 处**；`export function isOfflineError` 恰好 1 处。
- 判定函数体里**必须**有 `isOfflineError === true`，且**不得**出现 `instanceof`。
- 离线回落的分支必须有 `log.warn`（否则"为什么离线还能看 / 为什么改不了"无从查起）。
- 反证（`verify-falsify-logredaction.mjs` **7/7**）：重新加一份 `export class OfflineError` ⇒ **红**。

**处置**：`parallel-store.ts` 里那两份声明**删掉**，改为
`export { OfflineError, isOfflineError } from './offline'`（转发，保留原有 import 路径）。

★★ **顺带踩到一个 JS 语义坑，值得单独记**：
`export { X } from './y'` 是 **re-export**，它**不会**在本文件的作用域里绑定 `X`。
于是本文件自己要用的 `isOfflineError` 必须**再 `import` 一次**。
而报错位置是**调用点**（`Cannot find name 'isOfflineError'`），
读起来像"调用点忘了 import"，真因在 re-export 的语义。

**推广**：★ **"现在没出问题"与"这样是对的"是两件不同的事。**
凡是"两处声明同一事实"的地方，问一句：
**它们靠什么保持一致？** 如果答案是"我照着抄的"或"恰好用的是某个宽松判定"，
那它就是在等一个人把它改坏。
★ 把一个类型集中到一处之后，**顺手钉住"判定必须用标记字段"** ——
那是让跨打包边界仍然正确的唯一原因，也是这条路径上最容易"被规范化掉"的东西。

## #16 【已修·判据教训】`[].every()` 恒为 `true` —— 判据在**空集合上退化成永远绿**

**症状**：一条判据是"契约里的每个 kind 都有处理分支"，写成
`[...reqKinds].every((k) => caseKinds.has(k) || preKinds.has(k))`。
它**通过了**，而且看起来完全合理。

而实际上是：`reqKinds` 是**空集**，`[].every(...)` **恒返回 `true`** ——
那条判据**什么都没验**。

**根因**：我在别处写了一个 `stripLiterals()`（剥注释与字符串字面量，
见 #14 的教训），然后在第 9 节**顺手也用了它**去读消息契约：

```ts
| { kind: 'par.list' }        // ← 这个 'par.list' 本身就是**字符串字面量**
```

⇒ 被剥成 `| { kind: '' }` ⇒ `kind:\s*'([^']+)'` 一个都匹配不到 ⇒ 集合为空。
而**空集合让 `every` 与 `!some` 这类断言全部恒真**。

★★ **这是本仓第三次踩"门禁退化"。** 前两次：
- `#11` 幽灵依赖：`check_deps.mjs` 改成"先剥字符串"后**检查数从 27 掉到 0**，
  门禁退化成永远绿，而它打印的「检查 0 处」看起来完全正常。
- `#17`（akso-vault）同样在 `check_deps.mjs` 上。

⇒ 三个不同的人/三次不同的事故，**同一个失败形态**：
**为了让判据"不被自己的注释弄红"而引入的剥离，顺手把判据要读的东西也剥掉了。**

**判据**：

- **规则**：`stripLiterals` 只用于"**怕被自己的解释性文字弄红**"的断言。
  凡是要**读字符串字面量的内容**的断言，必须用**原始**源码。
- **`@ts-expect-error` 也是注释** ⇒ 它在剥离后查不到（本轮的第二个症状）——
  同样用原始源码。
- **所有"集合可能为空"的判据必须加自证前提**：
  本轮加了 `check('判据前提：契约 kind 集合非空', reqKinds.size > 0)` ——
  它当场把"26 个"打出来，如果哪天又变 0，**红的是前提那条**，
  而报错会直接说"集合为空"，不再伪装成"契约不同步"。
- **反证必须真的加一个 kind**（`verify-falsify-logredaction.mjs` 第 ⑧ 条）：
  在契约里加 `| { kind: 'definitely.not.implemented' }` ⇒ 判据**必须红**。
  ★ 只有这条反证能证明"空集问题已修" —— 别的反证都验不到它。

**处置**：第 9 节的读取分两路 —— 结构断言（有 `default` / 有 `log.error`）
用剥过的源码；**任何要读 kind 名的地方**用原始源码；
并补两条"集合非空"自证。

**推广**：★ **写 `every` / `some` / `includes` 类判据时，先问"集合会不会是空的？"**
空集合下的 `every` 恒真、`some` 恒假 —— 两者都是**静默的**。
★ 这条与 #10（"写完判据先问拆掉什么它才会红"）是同一个问题的两个面：
**"判据没在验东西"有两种成因** ——
① 它断言的性质永远成立（业务逻辑问题）；
② **它遍历的集合是空的**（数据/解析问题）。
第二种更隐蔽，因为判据的**文字**完全正确。

## #17 【已修】"某一类路径整类静默" —— 而日志的**级别选择**本身能让它继续静默

**症状**：`tab-rules.ts` 是七个隔离平面里的**网络平面**，而它**一行带级别的日志都没有** ——
只有 5 处 `diag()`（`storage.local` 的人读文本，**环形 60**）。

它的失败路径是**历史上最贵的那一类**（`PITFALLS #1`/`#8`）：
DNR 规则装不上 ⇒ **整个网络平面一起死**。而当时唯一的信号就是那 5 行 `diag()` 之一。

★★ 但真正值得记的不是"没日志"，而是**一个更深的形态**：

| 分支 | 后果 | 界面上像什么 |
|---|---|---|
| `addOne` 装 AUTH 规则失败 | `meta.authId` 不写 ⇒ 页签请求**不带正确 Bearer** | **像成功**（平台照样打开） |
| `addOne` 装 COOKIE 规则失败 | `meta.cookieId` 不写 ⇒ 既不回放也不剥离 | **像成功** |
| **两条都失败** | 页签**完全没有网络平面保护** | **像成功** —— 只是**以错误的身份在跑** |
| 移除规则失败 | **本该失效的旧规则继续生效** | 像"切了账号"（而请求还带上一个账号的头） |

⇒ 这是"静默失效"的最坏形态：**功能没生效，而它与生效长得一样**。

**根因**（两层，第二层才是本轮的新知识）：

1. 失败只写 `diag()`（人读文本、环形 60、会被高频埋点挤掉，见 `#14`），
   而**没有带级别的 `log.error`** ⇒ 不进 `appLogs`、不被级别过滤突出。
2. ★★ **"有日志"不等于"日志会说话"——级别选择本身能把它重新变成静默。**
   本轮我一度打算把"规则装上"也记成 `log.debug`；那是**对的**（中频轨迹）。
   但**失败**若也走 `debug`，而默认级别是 `info` ⇒ **生产环境一个字都不输出** ——
   于是我们"加了日志"，而缺陷依然静默。
   **同一个日志调用，`debug` 与 `error` 之间的差别就是"没日志"与"有日志"。**

**判据**（`tools/verify/verify-log-redaction.mjs` 第 10 节，**78 条**）：

- `addOne` 失败时**必须** `log.error`（且**仍要**写 `diag()` —— 人读文本进诊断包）；
- `applyBinding` 对"**有 token 却装不上 AUTH**"与"**COOKIE 规则未装上**"必须 `log.error`；
- 移除规则失败必须 `log.error`（它的方向与安装失败**相反**，必须能分开）；
- 反证（`verify-falsify-logredaction.mjs` **10/10**）：把那行 `log.error` **降级为
  `log.debug`** ⇒ **如期变红**。

★★ **这一节的判据自己又踩了 `#16` 那个坑的变体，两次**：

1. `getLogger('tab-rules')` 里的 **`'tab-rules'` 是字符串字面量** ⇒
   在 `stripLiterals` 之后变成 `getLogger('')` ⇒ 断言查不到。
2. 更隐蔽：要断言的 `AUTH` / `COOKIE` / `移除` 这些关键字
   **也都在 `log.error('...')` 的字符串里** ⇒ 同样被剥掉。

⇒ 同一个文件里必须**混用两种源码**：
找**标识符**（`log.error(` / `diag(` / `getLogger`）用**剥过的**；
找**字面量的内容**（`'tab-rules'` / `AUTH`）用**原文**。

★ 顺带一个反证器的小坑：反证第 ⑨ 条最初写成"把 `log.error(` 拆成两半"，
于是 **marker 字符串仍在源码里** ⇒ 判据不红 ⇒ 反证 `SKIP`。
**反证的缺陷版必须让被断言的那个字符串真的消失**，否则反证验的是空气。

## #18 【已修·判据教训】"整段里有安全痕迹" ≠ "每个值都安全" —— 判据的范围**又一次**错了

**症状**：新增了一条**静态**判据（第 11 节），验的是
"凭据值**没有**被交给 `log()`"（纵深防御，见下面的"为什么需要第二道"）。

它的实现是：取出一条 `log.*()` 的参数区，**如果里面有凭据标识符，
就必须同时有"存在性判断"的痕迹**（`有` / `无` / `缺` / `Boolean(` / `.length`）。

判据在真实代码上**通过**了（81/81）。看起来没问题。

**根因**：反证第 ⑩ 条把它打红了 —— 或者说，**它本该红而没红**：

```ts
// 缺陷版（反证注入）
log.info('device-poll：approved ⇒ ...',
  token, fernetKey ? '有' : '无', email ? '有' : '无');
//^^^^^ 裸 token：明文交给了 log()
```

判据给出的结论是"**缺陷版下仍然绿**" ⇒ 反证器报 `FAIL 这条验收是空断言！`

**为什么**：判据看的是"**整段参数区**里有没有 `有|无|缺`"。
而那段里 `fernetKey` 的 `'有'` 与 `email` 的 `'有'` **让整段合格** ——
于是旁边那个**裸 `token`** 被一起放过了。

⇒ 这是 `#14` 那条教训的**第二次出现**（规则 23 已经写过）：
> **判据的范围要按代码的真实结构划，不能按"我改过这个函数/这段参数"划。**

第一次是 `isEnforceable`（我把范围划成整个函数体，而真实的热路径只是缓存命中那一支）；
这一次是日志参数（我把范围划成整段，而真实要逐个值看）。

**判据**（修好之后）：

- 安全形态只有四种，且必须**紧贴该标识符本身**：
  `cred ? … : …`、`cred.length` / `cred?.length`、`cred.slice(`、`cred !== null`、`Boolean(cred)`；
- 其余一律视为"把值传了出去"（**逐标识符**判定，不看整段）；
- 反证 **⑩**（裸传 `token`）与 **⑪**（模板串插值 `${deviceCode}`）**各自变红**
  ⇒ 两种泄密形态都有反证背书。

**处置**：把"整段判定"改成**逐标识符 + 就近形态**判定。

## ★★ 顺带说明：为什么"运行时打码"之外还需要这一道静态判据

前 10 节验的都是 `log()` **运行时**会打码 —— 那是**一道**防线。
第 11 节验的是**根本没有把凭据交给 `log()`** —— 那是**第二道**。

★ 需要第二道的理由：**打码靠的是 `redact()` 里的 6 条正则，而正则会被绕过** ——
一个没见过的键名、一个被 Base64 过的值、一个被拼进 URL 的凭据，都可能漏过。
而"从不把明文交出去"**不依赖任何正则**。

★ 而这一类缺陷**在功能上看不出任何异常**：`log()` 会把它打码，
DevTools 里显示的就是打码后的值。⇒ **只有静态判据能发现它。**

**推广**：★ **写"某段里必须包含 X"这类判据时，先问"这段里会不会有多个东西，
而我其实只关心其中一个？"** —— 这是 `#14` 的同一条教训换个场景：
**范围划大了，判据就会在真实缺陷面前放行。**
★ 更一般的说法：**白名单式判据（"含有安全痕迹就放过"）必须问
"这个痕迹会不会来自**别的**对象？"** —— 会，就说明范围错了。
★ 而发现它的唯一方法是**反证**：把缺陷**真的注进去**，看判据红不红。
这一次反证不但发现了缺陷，还**否证了我自己的判据**（报"空断言"）。

## #22 【已修】日志"落盘注入点"从没被接线 —— 而判据盯错了 token

**症状**：接着做【两端日志】。查日志的**落盘路径**时发现：

    setSink(   →  只在 shared/log.ts 里出现（**定义它的地方**）

而 `log.ts` 的注释明写着它是**"可选的外部 sink（例如写入 `chrome.storage.local`
的诊断缓冲）"**。⇒ **全仓零调用。**

**后果**：`log.ts` 的环形缓冲（200 条）只在 **service worker 的内存里**，而
**MV3 空闲会回收 SW** ⇒

    故障发生 → SW 记进内存环 → 用户过一会儿去"导出诊断"
             → ql.diag 调 drain() 读环 → **环常常已经空了**

⇒ ★★ **最需要日志的时刻，日志已经没了。** 而诊断包恰恰是**事后**才去取的东西。

**根因**：★★ **判据一直是"`drain()` 有没有调用点"**（规则 22 那条 —— 当时确实是
**零调用点**，已修）。修好之后它**有**调用点了 ⇒ **那条判据变绿**，
而"**读得到吗**"这个问题**从来没有被问到**。

★ 这是规则 21 的**镜像**：那条说"安全靠约定时要问『违反了谁会知道』"；
这里是"**机制摆在那里时要问『它真的被接上了吗』**"。
与 v3.19 修掉的 `.side-collapsed` **同型**：接口/样式齐备，没人接线。

**处置**：

| 半 | 实现 |
|---|---|
| 写出去 | `setSink()` 在 SW **模块级**接线；攒 **10 条或 800ms** 批写（避免每条一次 IPC） |
| 读回来 | **新增 `restoreToRing()`** —— 启动时把上次落盘的记录放回内存环，`drain()`（诊断包）就都能看到 |
| 键 | `LOCAL_KEYS.logPersist = 'ql:log'`（集中声明，不裸写字符串） |

★ 三个刻意的设计（都写进了 `restoreToRing` 的注释）：
① **回灌不进 sink**（否则每启动一次就重写一遍，队列自己喂自己）；
② **不再打码**（进来的 `msg` 是**落盘前就已打过码**的）；
③ **不做级别过滤**（它们**确实发生过**，丢掉会让时间线缺段 —— 而缺段比多几条 debug 坏得多）。

**判据**：`verify-log-redaction.mjs` **第 14 节**（⇒ **106 条**）+ 反证 **19/19**。

★★★ **而判据设计本身踩了两次，两次都是"验的是空气"**：

**① 第一版写"文件里有没有 `setSink(` 调用"** ⇒ 通过。
而把 `installLogPersist();` 注释掉后 —— **判据仍然全绿**：

> `setSink((r) => {…})` 就在 `installLogPersist` 的**函数体内部**。
> "文件里出现过 `setSink(`"在**函数定义**处就已满足，**与"有没有调用它"无关**。

⇒ 反证器直接报 `FAIL 缺陷版下仍然绿 ⇒ 这条验收是空断言！`
⇒ 判据必须盯**模块级的那个调用**（`/^installLogPersist\(\);$/m`），
**不是"某处出现过某个 token"**。

**② 反证撞了两次"锚点"的坑**：

| 锚点 | 问题 |
|---|---|
| `installLogPersist();\nvoid replayLogPersist();` | **带 `\n` 的多行锚点没匹配上** ⇒ 文件没被改 ⇒ 判据当然绿 ⇒ **又报"空断言"** |
| `out.logs = drain();\n` | 同上 |

★ **规则 25 早就记过"锚点不要带 `\n`"** —— 这是它**第二次**咬人。
★ 而我自己写的新锚点也错过一次：我以为 `default` 分支里是 `throw new Error(...)`，
实际是 `return { kind, result: fail(...) }` ⇒ **锚点必须实测读出来，不能从记忆里写**
（规则 23：先实证打印，别猜）。

**③ 一条已有的判据因为我的改动而假红，而它指向了错误的根因**：
它用 `/async function dispatch\(…\)[\s\S]*?\n  \}\n\}/` **靠缩进猜函数收尾**；
我在文件顶部插入新的顶层代码后这个假设就不成立了 ⇒ 报出来的是
"`default` 没标 `@ts-expect-error`"（**而其实那条注释好好的**）。
⇒ 锚点应依赖**这段代码自己的内容**（那句独特的 `fail(`），**不依赖缩进/边界**。

**推广**：★★ **"接口摆在那里"与"它被接上了"是两件事，而前者会让判据变绿。**
· 有 `setSink` 的**定义** ≠ 有 `setSink` 的**调用**
· 有 `drain()` 的**调用点** ≠ 日志**活得到被 drain 的时候**
⇒ 每加一个"注入点 / 扩展点 / 可选通道"，**必须同时问**：
**"谁调它？调用点有判据吗？它产出的东西活得到被消费的时候吗？"**

★ 而"判据盯 token 还是盯调用"这件事有个可复用的问法：
**"把 X 注释掉，这条判据会不会红？"**
如果 X 的定义还在、判据就绿，那它盯的是**定义**，不是**接线**。

| # | 坑 | 教训 |
|---|---|---|
| ① | 想 `import { PNG } from 'pngjs'` —— **没这个依赖** | 仓库**没有任何 PNG 解码依赖**。为它新加一个正是**幽灵依赖**的入口（规则 14）⇒ 用 Node 内置 `zlib` **手写了最小解码器**（只支持 8-bit 非隔行 RGBA/RGB，遇到别的形态**明确抛错**而不是给错像素） |

| ③ | 按 `packages/extension/` 拼 ⇒ **仍然假红** | 运行时 manifest 在 **`dist/`**（构建拷过去），Chrome 实际找的是 `dist/assets/…`。**这条本身才是有价值的检查**：`build.mjs` 若忘了拷 assets，图标全裂而 `chrome://extensions` 只报"找不到文件" |

**推广**：★★ **"产物对"不能推出"源对"。**
验收通常盯着**产物**（页面上能不能看到、是不是方形），而**源是错的**时产物可以完全正确 ——

⇒ 每有一组"源 → 产物"，问三句：
1. **源在仓库里吗？**（不在 ⇒ 换台机器就再也生成不出来）
2. **源与产物一致吗？**（用**逐像素**或 hash 证明，不要靠"看起来像"）
3. **有没有判据能识破"源被换成别的东西"？**

   ⇒ **判据要盯"这个东西区别于冒牌货的那个性质"**，而不是"它存在"。

## #24 【已修】前端日志**结构性地**到不了落盘通道 —— 所以没人加日志

**症状**：审计日志覆盖面时出现一个**规律性**的现象，而不是零散的"忘了加"：

| 环境 | 文件数 | 有 logger 的 | 静默 catch |
|---|---|---|---|
| `background/`（SW） | 13 | **9** | — |
| `content/`（注入页面） | 7 | **1** | 30 |
| `ui/`（扩展自有页面） | 9 | **0** | **22** |

★ 三个环境的差距不是"勤快程度"的差距，而是**通道可达性的差距**：
`log()` 的环形缓冲与 `setSink()` 的落盘**都在 service worker 里**，
而 **content script 与扩展页面各有自己的 JS 环境** ——
它们调 `getLogger` 写进的是**另一个进程的内存**，那个环**永远不会**进诊断包
（诊断包由 SW 的 `ql.diag` 产）。

⇒ **在那两个环境里加日志是"白加"** —— DevTools 里看得到，导出诊断包时一条都没有。
**于是没人加**：这是"工具不可用 ⇒ 行为退化"的典型形态。

★★ 与 `PITFALLS #22`（`setSink()` 从没被调用）是**同一形态的第二处**：
机制只接到了 SW 这一端，另外两个环境从来没接上。
而 #22 修完之后，**判据变绿了**（`drain()` 有调用点、`setSink` 有调用点），
"其他环境够得到吗"这个问题**又一次**没被问到。

**判据**：`verify-log-redaction.mjs` **第 15 节**（⇒ **121 条**）+ 反证 **23/23**：

1. 契约两侧都有 `ql.log`；
2. `log.ts` 导出 `setForwarder` 与 `getForwardingLogger`，且**转发前调 `redact()`**
   （进通道的文本必须已打码是硬约定 —— 否则跨环境引入新的泄露面）；
3. SW 的 `dispatch` 有 `case 'ql.log'`，且**喂给 `restoreToRing()`**
   （进**同一个**环 ⇒ 诊断包与落盘自然带上它）；
4. ★ **`parallel.ts` 模块级真的调了 `setForwarder`** ——
   判据盯**调用**，不是"文件里出现过某个 token"（#22 那个坑的复用）；
5. 两条真实静默失败有留痕（`sendSafe` / `loadBrowserAccounts`）。

**处置**（全部实测）：

| 环节 | 做法 |
|---|---|
| 契约 | `\| { kind: 'ql.log'; records: LogRecord[] }` + 响应 `Result<{ accepted: number }>` |
| `log.ts` | 新增 `setForwarder(fn)` 与 **`getForwardingLogger(name)`** |
| SW | `case 'ql.log'` → `restoreToRing(records.slice(0, 50))`，并**额外落一条 `forensics`** |
| `parallel.ts` | 模块级装转发器 + 三条静默失败补留痕 |

★ 四个**刻意的设计**：

① **转发器用注入而不是 import 消息类型** —— 后者会让 `shared/log.ts`
   依赖 `shared/messages.ts`，而 messages 被 service-worker 引用 ⇒
   **耦合方向反了**（日志是最底层工具，不该知道业务契约）。注入
   `(rec) => void` 就够了，**而且可测**。
② **`getForwardingLogger` 不改变本环境行为** —— 它照样写本环境的 console/环。
   ⇒ 即使 SW 不可达，DevTools 里照样看得到（**转发是增强，不是替代**）。
③ **转发前再打一次码** —— 进通道的文本必须已打码，这是**通道级的约定**，
   不靠调用点自觉（规则 21 的同一条思路）。
④ ★ **`sendSafe` 用 `debug` 而不是 `warn`** —— 它是**正常路径之一**
   （SW 冷启期间必然发生几次），记 `warn` 会把 `ql:diag` 环形 60 里的真失败挤掉（规则 22）。
   ⇒ 而"排障时才发现"不够，所以 SW 侧对每条 `ql.log` **额外落一条 `forensics`**
     （结构化、不受级别影响，进诊断包）⇒ "前端什么时候发不出消息"**一直有痕迹**。

★ 还改对了一句**我自己写错的注释**：我先在 `parallel.ts` 写"记进 forensics"，
而 `forensics` 在 UI 侧**也是本环境的** ⇒ 那句话说不通。
⇒ 改成在 **SW 的 handler** 里真正落一条，并把注释改准。

**推广**：★★ **"工具不可用"会伪装成"没人用"。**
看到一个环境里某项实践**系统性缺失**（而不是零散遗漏）时，
先查**那件事在那个环境里能不能做成**，再查"要不要做"。

⇒ 三条可复用的问法：
1. **这个环境够得到输出通道吗？**（够不到 ⇒ 先修通道，否则加的日志是白加）
2. **判据盯的是"定义"还是"接线"？**（#22 的教训：盯调用）
3. **"我修好了"之后，还有哪个环境没接上？**（#22 修完 SW 就绿了，而 content/ui 从未接上）

## #26 【已修】`dist/` 里躺着 11 KB 的**源文件** —— 而它零引用、没有任何门禁会说话

**症状**：翻 `dist/` 找别的东西时顺手列了个清单：

    合计 392.8 KB / 24 个文件
    ...
    11.1 KB  assets/logo-master-422.png     ← ★ 这个是**源文件**

`logo-master-422.png` 是**图标派生链的起点**（422×422 的真 logo，
`Icon16/32/48/128` 都是从它来的）。它是 `dist/` 里**唯一一个 manifest 没引用的文件**。

**根因**：`scripts/build.mjs` 里那一行 ——

    cpSync(path.join(root, 'assets'), path.join(dist, 'assets'), { recursive: true });

`recursive` 把 `assets/` 下的**一切**都带进了扩展包。
而 `assets/` 是**"源 + 产物"混放**的目录（`logo-master-422.png` 是源、`Icon*.png` 是产物），
所以"整个目录拷过去"这个写法**从第一天起就是错的** —— 只是当时 `assets/` 里只有图标，看不出问题。

**为什么所有门禁都绿**：

| 已有的判据 | 它管什么 | 它管不管这个 |
|---|---|---|
| `check-dist.mjs` | manifest 引用的产物**存在** | ✗（多出来的它不管） |
| `verify-icons.mjs`（当时 39 条） | 4 档图标的**像素内容**对 | ✗（同上） |
| `npm run build` | 能构建 | ✗ |
| `chrome://extensions` | 能装载 | ✗（多一个文件不影响装载） |

⇒ ★★ **没有任何一条判据问过"这个目录里该不该有它"。**
而唯一会发现它的方式是**人去把 `dist/` 列一遍** —— 那不是机制，是运气。

★ 这与 `PITFALLS #20`（favicon **做好了但没人引用**）是**镜像形态**：
那边是「**产物存在 → 没人用**」，这边是「**源被打进产物**」。
两者的共同点才是关键：**"存在"与"该存在"是两件事，而本仓此前只验了前者。**

**处置**：

- `build.mjs` 改成**按文件名白名单**拷 `Icon{16,32,48,128}.png`
  （与已有的 `copyUiStatics` 同一条原则：**只拷运行期真正要用的**）；
- `verify-icons.mjs` 加**第 7 节**（⇒ **42 条**）：

  | 判据 | 为什么这样写 |
  |---|---|
  | `dist/assets/` 里**恰好**是那 4 档（**集合相等**） | ★ 不能写"每个该有的都在" —— 那对**多出来的**永远绿 |
  | 没有任何 `logo-*` / `src-*` / `*.svg` | 直接盯"**源文件**"这一类 |

- 实测：`dist` **24 → 23 个文件，392.8 → 381.7 KB**。

**推广**：★★ **"产物对"要问两件事：内容对不对**，**以及它该不该在包里**。

1. **打包用白名单，不用整目录递归。** `cpSync(dir, {recursive:true})` 会把
   **将来**任何人往那个目录里放的东西也带进去 —— 它的行为**随时间漂移**，
   而每一次漂移都是静默的。
2. **"源"与"产物"尽量不要放在同一个目录**。混放时，"整目录拷贝"必然出错，
   而人不会觉得那是错的（因为**当时**它恰好只有产物）。
3. ★ **判据写成"集合相等"**（`JSON.stringify(present) === JSON.stringify(expected)`），
   不要写成"每个预期的都在" —— 后者对"多出来的"**永远是绿的**。

## #27 【已修】"`manifest.json` 合法" ≠ "Chrome 装得上" —— 而失败信息只在 `chrome://extensions` 上

**症状**：本仓有十几条判据都读 `dist/manifest.json` 的**内容**
（版本号三处同步、`world: MAIN`、CSP、`entryPoints` 一一对应…），
而**没有一条验过"它真的能被 Chrome 装载"**。

**为什么这是个真空档**：下面这些错误**都让 manifest 保持合法**，
`check-dist` 依然绿、`typecheck` 依然绿、`npm run build` 依然绿：

- `content_scripts` 指向一个**不存在的产物**（改过 `entryPoints` 但忘了改 manifest）
- `background.service_worker` 路径写错
- 图标少了一档、或某档文件被改名
- manifest 里出现 Chrome 拒绝的字段（**当年 `urlTransform` 就是这么把网络平面整死的**）

⇒ **而失败信息只在 `chrome://extensions` 的卡片上**（一个红色错误）
**和装载时的 console 里**。人不去点开那个页面，就**永远不知道**。
用户看到的是"扩展装了但什么都不干"。

**处置**：新增 `tools/verify/verify-load.mjs`（**17 条**）——
真起一个 Chromium + `--load-extension`，验五件事：

| 节 | 验什么 |
|---|---|
| ① | 扩展**被装载**（能导航到 `chrome-extension://<id>/ui/popup/popup.html`） |
| ② | 产物齐全性（**分两类判**，见下） |
| ③ | 三个自有页面（popup / parallel / wheel）能开且**无未捕获错误** |
| ④ | ★ **SW 真的活着** —— 能应答 `ql.diag` **且回了 `logs` 数组**（⇒ 落盘通道在线，而不只是"注册了"） |
| ⑤ | 装载与开页面期间**没有致命错误** |

★ 它**不验**登录 / 列表 / 开页签 / 盒子 / 设备流 / 离线降级 ——
那些要**真实云端账号 + 真实内网平台**，**必须人工走一遍**（B7 的剩余部分）。
本脚本**不冒充**那部分覆盖。

**四条踩坑（写这个脚本的过程本身）**：

★★ ① **`headless: true` + 系统 Chrome 稳定版不加载扩展。**
  第一版拿到的 SW 一直等不到（15 秒超时），原因不是代码，是**浏览器**。
  ⇒ 必须 `executablePath` 指向 **`ms-playwright/chromium-<ver>/chrome-win64/chrome.exe`**
  （本仓 `verify-v310.mjs` 早就有 `findPwChromium()` —— **我该先读现成的脚本，而不是自己发明**）。

★★ ② **扩展 ID 从 `manifest.key` 推导，不要靠 `ctx.serviceWorkers()`。**
  `sha256(Base64(key))` 前 32 个 hex 位 → 映射 a–p（与 `check-dist.mjs` 同一算法）。
  headless 下 SW 是**懒启动**的，`serviceWorkers()` 常常是空的 ——
  靠它就等于"把可测的东西绑在一个不确定的时机上"。

★★★ ③ **content script 按设计不在 `web_accessible_resources` 里** ⇒ 用扩展协议**取不到它**。
  我第一版把**全部** manifest 产物都用 HTTP 取，于是 4 个 content script
  **全部报"缺失"，而它们就在磁盘上**。
  ⇒ **那条判据测的是访问控制边界，不是"文件在不在"。**
  ⇒ 分两类判：**能取的从页面内 `fetch()`**（图标 —— 它们必须在 `web_accessible` 里）、
    **不能取的查磁盘**（content script 与 SW）。

★★ ④ **而"取图标"也别用 Playwright 的 `page.request.get('chrome-extension://…')`。**
  同一批图标我先后看到"**能取到**"与"**全部 ERR**"**两次不同结果** ——
  根因是 Playwright 的 request 上下文**不在扩展的 origin 里**。
  ⇒ 用 `page.evaluate(() => fetch(chrome.runtime.getURL(rel)))`：
    那才是"扩展自己取自己的资源"，也正是 `web_accessible_resources` 真正约束的场景。

★ ⑤ **一条语法坑**：注释里写出「星号紧跟斜杠」会**提前闭合块注释** ⇒ `SyntaxError`。
  ★ 而我**在解释这个坑的那一行里又写了一遍** ⇒ 第二次才修对。

**推广**：**"配置合法"与"系统接受它"之间，每一个中间步骤都要有一条按「真的跑起来」验的判据。**

- 只要某个东西**只有人打开某个界面才会发现**（`chrome://extensions` / 服务端日志 /
  数据库里的一行），它就**必然会被漏掉** —— 而"漏掉"在这里长得和"没问题"一模一样。
- ★ 写这类脚本前**先读仓库里已经在跑的同类脚本**（本仓有 19 个）：
  它们里面的 `findPwChromium()` / `extensionIdFromKey()` **就是踩过坑之后留下的**。
  **自己发明一套 = 把那些坑重踩一遍。**

## #28 【已修】CSS 变量**引用了却解析不到**，以及**自引用** —— 浏览器都不报错

**症状（由"同一把尺子"的第五次应用发现）**：把"存在 vs 被使用"那把尺子量到 `src/ui/`：

    wheel.css: 品牌蓝 #1e6fff 出现 12 次（8 处 var(--acc, #1e6fff) 的 fallback + 4 处裸硬编码）
    theme.css: --sb-brand: #1E6FFF   ← 定义了一次
    ⇒ **同一个颜色散在 13 处，改一处必漂**

★ 而 `wheel.html` **既不加载 `theme.css`**、`wheel.css` **也没有 `:root`**
⇒ `--acc` **从未被定义** ⇒ 那 8 处 `var(--acc, #1e6fff)` **一直在用 fallback**。

**为什么"没被发现"**：`var(--x, fallback)` 是**合法**写法，浏览器不会报错。
真正危险的是**没有 fallback 的那种**：`var(--x)` 解析不到时**整条声明被丢弃** —— 那条 CSS 等于没写。

**处置**：给 `wheel.css` 加一个 `:root`，把 `--acc`/`--d` **显式定义成同一个值**，
去掉 9 处 fallback、把 4 处裸硬编码改成 `var(--acc)` ⇒ **品牌蓝从 13 处降到 2 处**
（`theme.css` 一处 + `wheel.css` 一处）。
新增 `tools/verify/verify-css-vars.mjs`（**15 条**）：逐页面按**真实 CSS 依赖链**
（`<link rel=stylesheet>` + 递归 `@import`）解析，断言
① 无「`var()` 无 fallback 又解析不到」② 无**自引用** `--x: var(--x)`。

★★ **整理时我自己踩了两次，两次都值得记**：

**第一次**：`readdirSync(UI, {recursive:true})` 返回的路径**可能是 Buffer 也可能含反斜杠** ——
★ 而真正的坑是下面这个。

**第二次（更值钱）**：我用**全局替换** `#1e6fff → var(--acc)` ——
**它把 `:root` 里那一行自己的值也换掉了** ⇒ 变成：

    --acc: var(--acc);     ← ★ 自引用，等于未定义！

⇒ ★★ **"全局替换"必须排除"那一处定义"。** 这是本仓"**替换会把不该动的也动掉**"的又一形态
（同族：`str.replace("", x)` 在每个字符间插入、跨多行正则吞掉相邻块）。

★★★ **而"截图逐字节相同"没能发现它** —— 我特意做了 6 张截图（3 档视口 × 2 主题）做前后对照，
结果**逐字节相同**，我一度以为"视觉零风险"成立。**实测发现那 6 张截的是空态**：
轮盘页要从 `chrome.storage` 读账号才渲染扇区，而脚本里没有账号 ⇒
**颜色根本没出现在画面里，前后当然一样。**

⇒ **教训：判据要盯"那个值真的被用到了"，不是"画面看起来一样"。**
"没变化"既可能是"改对了"，也可能是"**这次改动没进入被测路径**"。
★ 所以这类缺陷**只能静态查**（`verify-css-vars.mjs`），不能靠截图。

**★ 后来补做了这份对照（同一天，紧接着）**：把截图工具改成
**mock `par.list` + seed 存储** ⇒ 轮盘**真的渲染出扇区**（SVG 元素 33 个，截图 56.9 / 73.2 KB，
而空态是 38.9 / 51.4 KB），并实测：

| 检查 | 结果 |
|---|---|
| `--acc` 的 computed 值 | `#1e6fff` |
| 画面里**真的在用**品牌蓝 `rgb(30,111,255)` 的元素 | **有**（`circle.box-node-on fill`）★ 空态时**一个都没有** |
| 把 `--acc` 改成 `#ff0000` | 截图签名 **`f32568…` → `6ab882…`（真的变了）** |
| 还原后 | 签名**回到** `f32568…` |

⇒ ★ **"值不变 ⇒ 渲染不变"现在有判据了**；而上一轮那次"前后相同"是**空态巧合**。
★ 另一条副产品：`brandUsers` 只按 `fill/stroke/color/background` **精确等于**品牌蓝来找，
而 `--acc` 在颜色混合里被用作**输入**（改红后一个精确命中都没有，截图却变了）
⇒ **"画面变了但找不到精确命中的元素"**是正常的（`color-mix`/渐变）。
⇒ 所以**截图哈希**才是这类改动的主判据，"元素搜索"只作辅助。

**推广**：

1. ★ **CSS 变量是"隐式契约"**：`var(--x)` 与 `--x:` 可以在**不同文件、甚至不同页面**里，
   而没有任何工具检查它们配对。⇒ 变量必须**按页面的依赖链**验，不能全仓混着看。
2. ★★ **`var(--x, fallback)` 与 `var(--x)` 是两件事**：前者是**刻意的兜底**（不算缺陷），
   后者解析不到会让**整条声明消失**。判据必须区分 —— 混在一起会把正确的写法报成缺陷。
3. ★★ **"没变化"是个双向信号**：改完看到"完全一样"时，先问
   **"这次改动真的进入被测路径了吗？"** 而不是直接宣布"无副作用"。
   ★ 而验证它的办法是**把值改成一个明显不同的**（`#1e6fff` → `#ff0000`）看结论**会不会翻** ——
   **这既是"判据要能红"（规则 21），也是视觉工具唯一可信的用法。**
4. **全局替换前先数一遍锚点**：替换后要**复查**"我预期的那个数字还在不在"
   （本次就是靠 `#1e6fff 只剩 0 处（应恰好 1）` 这句自检发现的）。
