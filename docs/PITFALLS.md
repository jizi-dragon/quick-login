# 踩过的坑（quick-login）

> **为什么要有这个文件**：这里每一条都是**"看起来正常但其实是坏的"**那一类 ——
> 它们不抛异常、测试也未必覆盖，只是静默地变差。类型系统和构建都不拦这些。
>
> **格式（与 `akso-vault/docs/PITFALLS.md` 一致，五段）**：
> 症状 / 根因 / 判据 / 处置 / 推广。**编号是稳定 ID，永不重编**；已修的不要删，
> 改状态标注即可 —— 它的价值在于让下一个人知道**这里曾经坏过、以及坏成什么样**。
>
> **每条必须有可执行判据**。写不出判据，说明还没定位到根因。
>
> 本仓此前**没有**这个文件，这类教训散在 `CHANGELOG.md` 里。`CHANGELOG.md` 记的是
> "每次发布改了什么"，本文件记的是"**哪些错会静默发生、怎么一眼认出来**"——
> 前者是历史，后者是可复用的判据。

## #1 【已修】`urlTransform` 是 Firefox 专属 ⇒ 整个网络平面曾一起死掉

**症状**：多开时 HTTP 缓存平面失效，四个账号互相串缓存；而**更糟的是**——
COOKIE 与 AUTH 平面的规则也一起没生效。

**根因**：平面 4（HTTP 缓存）用 DNR 的 `redirect.urlTransform` 实现，
而**该字段是 Firefox 专属、Chrome 从未支持**（Chromium 以
`Unexpected property: 'urlTransform'` 拒绝）。关键在于
**`updateSessionRules` 是原子批量操作** ⇒ 同一批里的 COOKIE / AUTH 规则被连坐拒绝，
**网络平面全死**。而失败信息只说"属性不认识"，不指向"另外两个平面也废了"。

**判据**：`Get-ChildItem packages/extension/src -Recurse -Filter *.ts | Select-String -Pattern 'urlTransform\s*:'`
⇒ **零命中**。★ 必须匹配**作为键**的 `urlTransform:`，**不要**只搜这个词 ——
它在解释"为什么不用它"的注释里有 4 处，只搜词会**永远为红**。
已实测：精确判据零命中，且构造一个真实使用后**能红**。

**处置**：**已修**。改为页面层实现 + **逐条安装降级**
（一条规则被拒不再连坐其余）。

**推广**：★ **批量原子 API 的失败面是"整批"，不是"那一条"。**
用这类 API 时，问的第一个问题不是"这条对不对"，而是
**"这条错了会带走谁"**。同理适用于 `chrome.declarativeNetRequest.updateSessionRules`、
`runtime.sendMessage` 的批量场景、以及任何事务型批量写。

## #2 【已修】`shield-main.ts` 的四个平面**漏了 `?` 号** ⇒ 内网 http 站点全不生效

**症状**：内网形态是**纯 http**（`10.100.0.105`），而那四个平面的补丁**只对 https 生效**，
于是内网站点串号；而公网站点一切正常 ⇒ 报障时容易判成"内网平台的问题"。

**根因**：补丁里手写 origin 匹配时漏了 `?`（`https?` 写成了 `https`），
而**漏一个字符不报错**——它只是"这条分支永远不进"。

**判据**：`Select-String -Path packages/extension/src/content/shield-main.ts -Pattern 'https\?:'`
⇒ 命中数 == 需要 scheme 无关的平面数。

**处置**：**已修**（v3.10.9）。并由此引入"**scheme 必须数据化**"这条约定：
站点协议 hint 存在 `LOCAL_KEYS.siteSchemes`，不在代码里写死。

**推广**：**目标环境有两种形态时，第二种形态是最容易漏的。**
本仓的目标平台同时有公网 https 与内网 http ⇒ 任何"只在 https 下测过"的改动
都只覆盖了一半用户。

## #3 【已修】日志面曾**没有脱敏通道**，且 logger 命名空间分叉

**症状**：无 —— **改造前只有 3 处裸 `console.*`，都"看起来没用凭据"**。
所以"还没有凭据泄露"这件事**只是碰巧**。

**根因**：两个独立的问题叠在一起：

1. `console.debug('[ql-auto] submit rejected by server', { errorSeen })` 这种
   **对象直传**是典型形态 —— 今天 `errorSeen` 里只有计数，明天有人往里塞
   `{ username, password }` 做"排障方便"，凭据就出去了，**而没有任何东西会拦住**。
   本扩展**持有用户在各平台的真实口令**（填表要用），所以这条代价极高。
2. 服务端（`akso-vault`）同期还有第二套 logger 名的问题（那边已记为它的 #7）——
   这里写下来是为了记住**两端的日志形状应当一致**，否则读日志的人要多一次上下文切换。

**判据**：`node tools/verify/log-redaction.mjs` —— 37 条断言，两侧都测：

- **该打掉的**（漏了就是外泄）：`password=` / `"secret":` / `token:` / `Bearer` /
  `Basic` / URL 查询串里的 `device_code` 与 `user_code` / `fermeyKey` / 裸长十六进制；
- **不该打掉的**（过度匹配会让日志失去价值，于是有人去关掉打码 —— 那是下一条泄露路径）；
- **端到端**：`log()` 出来的东西（含**对象直传**与**分隔参数**两种形态）都不含凭据原文；
- **结构性**：`src/` 下除 `shared/log.ts` 外**零裸 `console.*`**。

★ 并做了**反证**（`tools/verify/falsify-log-redaction.mjs`，3/3）：
把 `formatArgs` 改成直接返回原文 ⇒ 验收如期变红；还原后逐字节一致。

**处置**：**已修**（2026-10-09）。新增两个共享模块：

```
shared/redact.ts   纯函数的打码规则（可单独测试）
shared/log.ts      getLogger(ns) —— 所有出口都只经由 log()，而 log() 无条件先打码
```

三条设计决定，理由都是"绕不过去"：

1. **打码在 `log()` 里，不在调用点。** 调用点靠自觉，而自觉会失效。
2. **先做 `%s` 替换、再打码。** 理由见 #4（这是实测踩出来的）。
3. **对象必须先序列化再打码**，且序列化**绝不能抛**（循环引用 / BigInt /
   `undefined`）。★ MV3 的 SW 里一个未捕获异常会**终止整个 worker** ——
   日志代码把业务带崩，比丢一条日志坏得多。

**推广**：**"凭据不入日志"必须是结构，不是纪律。**
与 `akso-vault` PITFALLS #1 是同一条推理的两个应用面。

## #4 【已修·判据教训】`%s` 会把"键"和"值"分开，于是打码**完全失效**

**症状**：`logger.info('password=%s', secret)` 打出来的日志里，
**口令是明文**，而单测 `redact('password=xxx')` 却通过。

**根因**：格式器如果只是把参数用空格拼起来，上面那句会变成
`password=%s secret` —— **`%s` 夹在键和值中间**，
打码规则看到的是"一个孤立的词"，于是**没有任何规则命中**。

★ 这是本轮最值得记的一条，因为**它的两层测试会给出相反的结论**：
纯函数层全绿（`redact` 本身没问题），只有端到端层会红。

**判据**：`node tools/verify/log-redaction.mjs` 第 4 节那条
「log() 里的分隔参数口令被打掉」。反证：把 `interpolate` 换回纯 `join(' ')`
⇒ 该条如期变红。

**处置**：**已修**。`formatArgs` 的顺序固定为
**先 `%s/%d/...` 替换 → 再拼多余参数 → 最后整体打码**。
顺序不能反：替换让"键 = 值"重新贴在一起，打码才有东西可认。

**推广**：★ **"打码函数是对的"与"打码在实际路径上生效"是两件事。**
凡是"先格式化再脱敏"的通道，都必须有一条**走真实出口**的用例 ——
只测纯函数会给出虚假的安全感。

## #5 【已修·判据教训】esbuild 摇树把没被 `import` 的导出删掉 ⇒ 验证脚本"找不到函数"

**症状**：验证脚本从 `shared/log.ts` 解构 `redact` / `REDACTED` 时报
`TypeError: redact is not a function`，而源码里明明写着 `export function redact`。

**根因**：`log.ts` 只 `import { redact } from './redact'` ⇒ 打包时
**esbuild 把 `redact.ts` 里没被用到的导出整段摇掉**（包括 `REDACTED`）。
导出在**源码**里存在、在**产物**里不存在 —— 而报错只指向"不是函数"。

**判据**：验证脚本能取到它需要的每个导出（现由 `log-redaction.mjs` 隐式覆盖：
它解构了 `redact` / `REDACTED` / `formatArgs` / `getLogger` / `setLogLevel` / `drain`）。

**处置**：**已修**。`log.ts` **显式转发**打码 API：

```ts
export { redact, REDACTED, REDACTION_RULES } from './redact';
```

这不只是整洁 —— 它让 `log.ts` 成为日志相关的**唯一公开面**，
调用方不会去 import 一个"其实不会被打进产物"的内部模块。

**推广**：**`export` 是源码层的概念，产物里有什么由打包器的摇树决定。**
凡是用"现场转译源码"的方式做验收（本仓 `tools/verify/log-redaction.mjs` 就这么做），
入口的导出面必须与验收脚本的需要一致。

## #6 【已修·判据教训】仓库根算错一层，**不报错、只指向错目录**

**症状**：脚本报 `Could not resolve ".../tools/packages/extension/src/shared/log.ts"`
—— 路径里多了一层 `tools/`，而**脚本本身没有任何语法或运行时错误**。

**根因**：惯用法 `path.resolve(path.dirname(fileURLToPath(import.meta.url)), '..')`
在**一层深**的目录里（`tmp/x.mjs`）正好是仓库根；搬到 `tools/verify/`（**两层深**）后
必须写成 `'..', '..'`。**少一层不报错，只会指向错目录。**

**判据**：把表达式**真的求值**并断言等于仓库根。本仓的做法是脚本开头打印
`ROOT = ...` 并在启动时对关键路径做 `existsSync` —— 让"指错目录"立刻可见。

**处置**：**已修**。`tools/verify/log-redaction.mjs` 用 `resolve(HERE, '..', '..')`，
并在注释里写明"少一层会静默指向 `tools/`"。
★ 本轮**又踩了一次**：临时调试脚本 `debug-bundle.mjs` 第一次写的就是一层，
报错信息看起来像"esbuild 配置有问题"。

**推广**：★ **这类错误的特征是"报错指向别处"。**
凡是脚本依赖"我在目录树的第几层"，就把它**打印出来**或**断言**一次 ——
靠肉眼数 `..` 的个数，迟早数错。

> **同一根因的相反表现（本仓无 `.gitattributes`，`akso-vault` 有）**：
> 两个仓库对行尾的处理**方向相反**，所以同一个"行尾不对"的毛病在两边长得完全不一样：
>
> | 仓库 | `.gitattributes` | 索引里存的 | 磁盘上检出的 | 症状 |
> |---|---|---|---|---|
> | `akso-vault` | 有（`*.py text eol=lf`） | LF | **LF** | 脚本把文件写成 CRLF ⇒ `git status` 长期一堆**假 `M`**，真的改动看不见 |
> | `quick-login` | **无** | LF | **CRLF** | 每次提交打印一堆 `LF will be replaced by CRLF` 警告（**装饰性**，内容无差异） |
>
> ★ 本仓实测**没有**假 `M`（提交后 `git status` 干净），所以**刻意不加** `.gitattributes`：
> 加它会对上百个已跟踪文件做一次重规范化，产生一个巨大且无实际收益的 diff。
> ⇒ **"看到警告就改配置"不是判据；先确认它有没有造成实际损害**（这里是"有没有假 M"）。
> 本仓的脚本都在 Windows 上跑、或由 `npm` 调起，shebang 的行尾不会成为问题。

## #7 【已修·判据教训】`window===window.top` 判顶层，在 `srcdoc` iframe 里会给出反直觉结果

**症状**：自动填表在密码框位于同源 `srcdoc` iframe 时，**顶层 frame 也要去填**，
但脚本按"只有子 frame 才填"的分支走 ⇒ 填不上，而日志里"看起来走对了分支"。

**根因**：`about:srcdoc` frame **不会被 `<all_urls>` 的 content script 注入**
⇒ "谁负责填密码"不能按"我是不是顶层"来决定，必须按
**"我能不能拿到那个 `iframe.contentDocument`"** 来决定。

**判据**：`docs/CODEBASE_OVERVIEW.md` 里记录的填充分工
（顶层 frame：用户名 + 访问 srcdoc iframe 填口令 + 勾协议 + 提交；
子 frame：仅兜底填自身 frame 内的口令）必须与实际分支一致。

**处置**：**已修**。填充逻辑按"能否访问 `contentDocument`"分支，
而不是按 `window === window.top`。

**推广**：**"我在哪"和"我能碰到什么"是两件事。**
按位置分支容易写对、也容易漏；按能力分支更贴近真实约束。

## #8 【已修·设计确认】`updateSessionRules` 是**原子批量**，必须逐条降级

**症状**：新增一条 DNR 规则后，**别的平面的规则也一起失效**，
而报错只说"新加的那条不认识"（见 #1 的实测）。

**根因**：Chrome 的 `updateSessionRules` 对整批做原子校验 ——
一条不合法，整批不生效。⇒ "新加一条规则"这个动作的**失败面是整个网络平面**。

**判据**：`tab-rules.ts` 必须是**逐条安装**（每条单独调一次），
并记录每条的结果；而不是把 N 条拼成一个数组一次提交。

**处置**：**已修**。逐条安装 + 每条单独捕获。

**推广**：**"加一条"的风险不等于"那一条"的风险。**
用批量原子 API 时，新条目的爆炸半径是**整批**。

## #9 【已修·设计确认】身份类 cookie 黑名单必须**集中声明**

**症状**：`mergeCookieSnapshot` 的 token 门禁与 `IDENTITY_COOKIE_BLACKLIST`

**根因**：黑名单是"同一件事的两个声明点"。

**判据**：身份键名单**只在一处**声明，其余地方引用它。

**推广**：与 `akso-vault` AGENTS.md 规则 14 同形 ——
**同一事实不要有两处声明**。两处各写一遍，迟早出现"改了一处、另一处没改"。

## #10 【已修·设计确认】验证脚本必须入库，**`tmp/` 是 gitignored**

**症状**：20 个验证脚本曾在 `tmp/` 下，`git ls-files tmp/` = **0** ⇒
换机器 / 新 clone / CI **一个都拿不到**。同类损失此前已发生过一次
（`tools/e2e/` 整套在收束清理中被删）。

**根因**：`tmp/` 是运行产物的目录（Chrome 档案几百 MB，不该入库），
但"脚本"与"脚本的产物"被混在了同一个目录里。

**判据**：`git ls-files tools/verify/` 的条数 == 该目录下的脚本数；
且 `git ls-files tmp/` 中的 `.mjs`/`.ts` 数 == 0。

**处置**：**已修**。脚本迁到 `tools/verify/`（入库），运行产物留在 `tmp/`（不入库）。

**推广**：★ **"临时"这个属性会传染。**
把脚本放进 `tmp/` 的那一刻它就被判了死刑，而**没人会注意到**，
因为文件在本地一直在、跑起来也一直正常。

## #11 【已修·判据教训】幽灵依赖：`node_modules` 里有 ≠ 能复现

**症状**：换机器 `npm ci` 后所有验证脚本报"找不到模块"，
而开发机上**一直跑得好好的**。

**根因**：**3 个幽灵依赖**（`playwright-core` 全部脚本用、`@peculiar/x509` 与
`reflect-metadata` 3 个自签 https 脚本用）只存在于 `node_modules/`，
`package.json` 与 `package-lock.json` 里都没有。
它们来自历史上某次 `npm install --no-save`。

**判据**：`npm run check-deps` ⇒ `DEP_OK`。
★ 该门禁自身也踩过坑（详见 `tools/check_deps.mjs` 的注释）：
第一版在源码上跑正则 ⇒ 假阳性（把注释里的 `import` 当依赖）；
改成"先剥字符串"后 ⇒ 说明符被清空、**检查数从 27 掉到 0，门禁退化成"永远绿"**，
而它打印的「检查 0 处」看起来完全正常。现在它带自检：
一处三方模块都没扫到就报 `DEP_SUSPECT`。

**处置**：**已修**。三个依赖写进 `devDependencies`；加 `npm run check-deps` 门禁。

**推广**：★★ **"能跑 ≠ 可复现"。**
加依赖一律 `npm install --save-dev`；`--no-save` 装上的东西会在
换机器时**同时消失、且只在别人的机器上暴露**。

> 这条与 #10、以及 `akso-vault` PITFALLS #11 是同一条主线的三个面：
> **"在我机器上是对的"这件事，不能作为判据。**

## #12 【已修】有三个写日志的出口，只有一个是受控的 —— `forensics` / `diag` **绕过打码**

**症状**：源码里"零裸 `console.*`"（判据绿）、`shared/log.ts` 的打码 37/37 通过、
诊断包能正常导出。一切看起来都对。

而实际上扩展端有**三个**把信息写出进程的出口：

| 出口 | 落点 | 当时是否打码 |
|---|---|---|
| `shared/log.ts` 的 `log()` | DevTools + 环形缓冲 | ✅ 强制打码 |
| `forensics()` | `storage.local['ql:forensics']`（**环形 120 条**） | ❌ **无** |
| `diag()` | `storage.local['ql:diag']`（**环形 60 条**） | ❌ **无** |

后两个的产物会**进诊断包被一键导出** —— 一条凭据进 `forensics`，
就等于**永久落在磁盘上、并且被导出去**。

**根因**：安全保证建在**约定**上，而不是**机制**上。
`content/auto-login.ts` 的注释写着"密码/用户名绝不入日志"，7 个 `report()` 调用点
**当时确实遵守了**（只传 `attempts` / `reason` / `errorSeen` / `btnText`）。
但：

- 载荷是 `{ tabId: sender.tab?.id, ...p }`，而 **`p` 完全由内容脚本决定**；
- 没有任何东西阻止下一个人写 `report('x', { password })`；
- `forensics` 是 `export` 的 —— **任何模块都能直接调**。

⇒ "我当时检查过所有调用点"不是一种可持续的保证。

**判据**：

- `node tools/verify/verify-forensics-redaction.mjs`（**25 条**）。
  它不是读代码猜，而是**真的把 `parallel-session.ts` 求值、真的调 `forensics()`**，
  再读回 `storage.local` 里那一行 —— 验的是将要发布的那份代码。
  覆盖 `password` / `accessToken`（复合键名）/ 嵌套 `userPassword` / 值里嵌的凭据；
  **反向**：`tabId` / `attempts` / `reason` / 非敏感字符串必须**保留**
  （吞掉它们 = 诊断包失去价值）；环形上限 120 与"留最新"不许被改坏；
  循环引用 / `BigInt` / 函数 / `Symbol` **绝不抛**（MV3 里未捕获异常会终止 worker）。
- 反证：`node tools/verify/verify-falsify-forensics.mjs`（**3/3**）——
  ① 摘掉 `forensics` 的打码 ⇒ 红；② 摘掉 `diag` 的 ⇒ 红；
  ③ 把敏感键名单退化成只剩裸 `password` ⇒ 红（复合键名 `accessToken` 漏掉）。

**处置**：`shared/redact.ts` 新增 `redactDetail()`（对象级、按**键名**判定，
与既有按**值形状**判定的 `redact()` 互补），`forensics` 与 `diag` 的**落盘点**
强制过它。键名匹配用**小写包含**而非相等 —— `accessToken` / `userPassword`
这类复合键名比裸 `password` 更常见，而漏掉它们的代价是明文入库。

**推广**：★ **"零裸 console"只证明了"没有绕过 A 通道"，证明不了"没有 B 通道"。**
凡是"安全靠约定"的地方，问一句：**这条约定如果被违反，谁会知道？**
答不上来就说明它是约定而不是机制。
★ 找这类洞的方法是**枚举出口**（谁会写到进程外？），而不是搜索已知的坏模式。
本仓的出口有三个：`console` / `chrome.storage` / 网络。

## #13 【已修·判据教训】花括号配平从**签名开头**数，会被参数表里的 `{}` 骗到

**症状**：一条"断言某函数体里调了 `redact()`"的结构判据**恒假**（假红），
而且它两次假红的原因是**两个不同的**坑。

**根因**（两次都值得记）：

1. **第一版**用 `ps.indexOf('function ' + name + '(')` 定位 —— 而实际声明是
   `export async function forensics(`，前面有 `export async` ⇒ **找不到**，
   函数体返回空串，`''.includes('redact(')` 恒 `false`。
2. **第二版**改成正则后**仍然假红**：花括号配平**从签名开头**开始数，
   而参数表里就有 `detail: Record<string, unknown> = {}` ——
   那个 `{}` 让 depth 先 `+1` 再 `-1`，于是**数到参数表末尾就归零了**，
   只截到 81 个字符（正好是签名那一行）。

**判据**：

- 定位函数体必须先用 `)\s*{` **跳过参数表**，从函数体的 `{` 起配平。
- ★ 并且**"找不到函数体"必须判失败**，不能静默返回空串、再靠后续断言碰运气 ——
  那样失败信息会指向"没调 `redact`"，而真因是"判据没找到函数"。
- 本轮的做法：先加两条 `check('能定位到 X 的函数体（判据自身的前提）')`，
  让"前提不成立"与"断言不成立"在输出里**分得开**。

**处置**：`tools/verify/verify-forensics-redaction.mjs` 的 `bodyOf()` 按上述写法。

**推广**：★ **写"代码结构"类判据时，先验证"我能拿到那段代码"。**
  拿不到时的表现是"断言为假"，而它读起来像"代码有问题" ——
  于是你会去查**被测代码**，而问题在**判据**。
  ⇒ 结构判据要有一条**自证前提**的断言（"我确实取到了这段代码"）。

## #14 【已修】日志系统**没有闭环**：产出的日志没人读，热路径又把它挤掉

**症状**：`shared/log.ts` 打码 37/37 通过、"零裸 `console.*`"全绿、`forensics` 也已收口。
**看起来日志这块已经做完了。**

实测（2026-10-09）却发现三件互相独立的事：

| 事实 | 后果 |
|---|---|
| `shared/log.ts` 只被 **1 个文件** import（`content/auto-login.ts`，取 `getLogger`） | 七个隔离平面的实现**一行日志都没有** |
| `drain()` 的调用点是 **0** | 日志只进 DevTools 控制台，**诊断包里一条都没有**；SW 一被回收就永远看不到 |
| `isEnforceable()` 的**缓存命中**每次都写 `diag()` | 它每次导航 / 请求判定都会走到 ⇒ `ql:diag`（**环形 60**、45 个写入点）被刷满 |

第二、三条要连起来看才是完整的病：
**唯一落盘的文本通道是个稀缺资源，而它被热路径占满了。**

**根因**：

1. **通道没有分工。** 三个出口（`log()` / `diag()` / `forensics()`）各自的
   **容量、持久性、用途**从未写下来 ⇒ 下一个人只会挑"看起来最方便的那个"。
   `diag()` 因为写 `storage.local`（SW 重启后还在），看起来最"可靠"，
   于是连"缓存命中"这种热路径也往里写。
2. **没有人问"谁来读"。** 加日志时想的是"写上"，没想"导出来时它在不在里面"。

**判据**（`tools/verify/verify-log-redaction.mjs`，**49 条**）：

- 第 6 节**闭环**：`drain()` 至少一个消费者；`ql.diag` handler 里 `out.logs = drain()`；
  诊断包的 `bundle` 里含 `appLogs` 与 `logLevel`。
- 第 7 节**三通道分工**：`isEnforceable` 的**缓存命中分支**里没有 `diag()` 调用
  （且必须有 `log.debug` 轨迹 —— 降级不是删掉）；同时反查 `void diag(` **仍然存在**
  （否则"降级"会被误读成"日志都该删"）。
- 反证（`verify-falsify-logredaction.mjs`，**6/6**）：拆掉 `drain()` ⇒ 红；
  拆掉 `appLogs` ⇒ 红；把热路径改回 `diag()` ⇒ 红。

★★ **这一节的判据本身错了两次，两次都值得记**：

1. **第一次假红**：我写"整个 `isEnforceable` 里没有 `diag()`"，而我在旁边
   解释了"这里原先写的是 `diag(...)`" —— **注释把它弄红了**。
   同一个坑在本仓是**第四次**（另见 #1 `urlTransform`、#4、#13）。规律：
   **"解释为什么不用 X"的文本必然包含 X。** ⇒ 判据要先剥注释与字符串字面量。
2. **第二次仍假红 —— 而这次推翻的是判据的「范围」，不是实现**：
   实证打印函数体后发现，函数里**另外两处** `diag()`（停用名单 / 授权实查）
   **每个 host 只走一次**（之后进 `enforcement` 缓存），**根本不是热路径**，
   留在 `diag()` 里是对的。真正每次调用都走到的是**缓存命中那一支**。
   ⇒ 判据必须落在**那个具体分支**上。
   ★ 教训：**判据的范围要按代码的真实控制流划，不能按"我改过这个函数"划。**

**处置**：

- `ql.diag` handler 增加 `out.logs = drain()` 与 `out.logLevel`；
  前端诊断包增加 `appLogs` / `logLevel` ⇒ 日志**有了消费者**。
- `isEnforceable` 缓存命中那行从 `diag()` **降级为 `log.debug()`**：
  写内存（环形 200）+ DevTools，默认 `info` 级 ⇒ **生产零存储开销**，
  排障时 `setLogLevel('debug')` 才出现。
- 三通道分工写进 `parallel-session.ts` 的注释与本节：

  | 通道 | 存储 | 谁该用 |
  |---|---|---|
  | `log.debug()` | 内存环形 200 + DevTools | **热路径**（默认静默） |
  | `diag()` | `storage.local` 环形 60 | **罕见但关键**：失败 / 降级 / 状态跃迁 |
  | `forensics()` | `storage.local` 环形 120 | **结构化事件**（可按字段过滤） |

**推广**：★ **"加日志"包含三件事，缺一件就等于没加**：
① 有出口、② **有人读**、③ **有用的那条活得到被读的时候**。
只做①会得到"日志系统很完整，但排障时什么都看不到"。
★ 判断"某条日志会不会挤掉别的"的方法：看**它所在的那条控制流多久走一次**，
而不是看"它是不是写在一个重要函数里"。
